# 案例：部署与数据保全

## 背景

部署是否正确，不能只看仓库中的版本文字。实际进程可能使用另一份代码、解释器或预处理目录；数据卷可读也不代表运行账号可写。迁移还需要保留任务历史与报告，避免“服务恢复”掩盖数据丢失。

## 处理流程与判断

既有维护说明记录了以下核对顺序：

1. 先确认活动和排队任务，保存代码身份、配置、数据库与历史产物的备份，再正常停服。
2. 核对进程实际工作目录、Step1 路径及解释器、Step2 提交与前端代理，区分源码状态和运行状态。
3. 核对运行账号能否写入数据目录。既有记录包含共享存储写入受限时转存到可写本地盘的处理；保留原件并保持容器引用对应。
4. 恢复后检查任务状态、已登记报告哈希和结果接口；回滚方案需要同时匹配代码与数据路径。

| 工程判断 | 原因 |
| --- | --- |
| 记录真实运行来源 | Git 提交或文档版本不能单独证明进程正在使用它 |
| 保留旧数据与原件 | 新路径可用不等于迁移完整，清理原件会缩小回滚空间 |
| 将私有配置放在公开仓库之外 | 展示部署判断无需公开账号、地址、凭据或原日志 |
| 交叉检查状态、哈希与接口 | 进程存活只说明一个层面，不能替代数据和消费路径检查 |

## 验证与取舍

[验证文档](../validation.md)保留当时的任务、报告哈希与接口检查摘要。本次未连接原数据库、重跑迁移或变更服务，历史记录不计入本次公开示例测试。

这些材料支持说明一次维护中的核对方法，不证明已有全故障演练、自动备份体系或 SLA。公开仓库不分发生产配置、部署凭据或迁移脚本，也不声明合作团队内测产品的部署成果属于个人独立实现。
